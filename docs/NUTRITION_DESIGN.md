# 健身营养指标功能设计与实现

## 目标

为每道菜提供可追溯、可修改的营养估算：既能看到每种食材贡献多少，也能看到整道菜总计。营养值是辅助记录，不作为医疗、诊断或个体化治疗建议。

## 第一版只做的核心指标

| 优先级 | 指标 | 单位 | 用途 |
| --- | --- | --- | --- |
| P0 | 热量 | kcal | 控制全天能量摄入，增肌或减脂都需要关注 |
| P0 | 蛋白质 | g | 肌肉修复与训练恢复的核心指标 |
| P0 | 碳水化合物 | g | 训练供能与恢复 |
| P0 | 脂肪 | g | 完整呈现三大营养素和能量来源 |
| P1 | 膳食纤维 | g | 衡量食物质量、饱腹感和膳食结构 |
| P1 | 钠 | mg | 中式菜肴中酱油、盐和调味料容易使钠偏高 |
| 派生 | 蛋白质密度 | g/100 kcal | 更直观比较同等热量下的蛋白质含量 |

饱和脂肪、添加糖、钾可以作为第二版指标。维生素和矿物质种类很多，第一版不在主界面展开，避免信息过载。

## 页面设计

### 菜谱录入

每个食材增加三个营养计算字段：

- 可食用重量（克）：营养计算必须有可换算为克的重量。
- 标准食材：例如“鸡胸肉（熟）”“花生油”“生抽”，关联本地营养数据库记录。
- 匹配状态：已确认、自动匹配待确认、无法匹配。

用户仍可保留“2 个”“少许”等原有文字用量，但没有克数时该食材不计入总值，并明确显示“缺少重量”。油、糖、盐、酱油等调味料必须作为食材参与计算，不能忽略。

### 设置

设置页提供六个独立复选框：热量、蛋白质、碳水、脂肪、膳食纤维和钠。用户可以只显示自己关心的项目，也可以全部取消。选择结果保存在 IndexedDB 本地设置中，并随 ZIP 业务备份导入导出；列表、详情与推荐结果使用同一选择，不建立账号或上传偏好。

### 菜谱详情

最上方只显示用户在设置中勾选的指标。蛋白质密度作为辅助信息保留在详情中，不进入六项显示开关。

整道菜默认展示“全菜总计”。如果用户填写成品总重量，则额外显示“每 100g”；以后可以增加“我吃了多少克”，但不恢复默认份数，也不与人数推荐混用。

## 计算规则

营养数据库统一保存每 100g 数值。每种食材贡献值：

`食材营养值 = 可食用重量(g) ÷ 100 × 数据库每100g营养值`

`整道菜总计 = 所有已匹配食材贡献值之和`

`每100g成品 = 整道菜总计 ÷ 成品总重量(g) × 100`

`蛋白质密度 = 蛋白质(g) ÷ 热量(kcal) × 100`

第一版不自动应用烹饪营养保留系数，也不猜测吸油率。食材用生重还是熟重必须与所选标准食材一致，并在界面显示。所有结果保留内部高精度，显示时热量取整数，克数保留一位，钠取整数。

## AI 与营养数据库的边界

- AI 可以根据图片或菜名生成食材清单，并尝试给出重量建议。
- AI 返回的营养数字不直接入库，也不参与总计，避免模型编造数值。
- 本地规则使用“标准食材 ID + 克数”从营养数据库确定性计算。
- 自动匹配必须允许用户确认或更换；没有确认的估算显示黄色提示。
- 图片无法判断油、盐、酱汁用量时，必须标记为“可能低估”，不能显示为精确值。

## 本地优先数据结构

```ts
interface NutrientValues {
  energyKcal: number;
  proteinG: number;
  carbohydrateG: number;
  fatG: number;
  fiberG: number;
  sodiumMg: number;
}

interface IngredientNutritionLink {
  foodId?: string;
  grams?: number;
  weightBasis?: "raw" | "cooked";
  matchStatus: "confirmed" | "suggested" | "unmatched";
}

interface FoodReference {
  id: string;
  name: string;
  aliases: string[];
  nutrientsPer100g: NutrientValues;
  source: "usda-fdc" | "curated" | "user";
  sourceRecordId?: string;
  sourceVersion: string;
}
```

菜谱保存食材关联和克数，营养总值在读取时由固定版本本地库重新计算。ZIP 备份包含菜谱营养关联和显示偏好，不包含远程服务密钥。

## 数据来源

应用随包内置 7,342 条标准食品记录，来自 USDA FoodData Central Foundation Foods 2026-04 与 SR Legacy 2018-04。构建脚本从官方 JSON 中提取本功能需要的六项指标，去除完全重复名称和缺少核心营养数据的记录，生成约 1.7 MB 的只读本地数据文件。USDA 数据以 CC0 提供，可在应用内离线搜索和计算，不依赖 API Key，也不发送菜谱或身体数据。

当前本地中文别名覆盖常见肉蛋奶、主食、蔬果、豆制品、坚果、食用油和调味料；英文标准食品名称仍完整保留，可继续逐步扩充中文别名而无需更换菜谱数据结构。数据生成方式记录在 `scripts/generate-nutrition-data.mjs`，来源版本固定，保证相同输入得到相同结果。

不要给“番茄炒蛋”“红烧肉”等菜名硬编码一个固定营养值：同一道菜的鸡蛋数量、肉的肥瘦、用油和糖差异很大。应根据当前菜谱的食材与重量计算，并标明完整度和估算范围。

## 分阶段实施

1. 已完成：六项营养求和、蛋白质密度、缺失食材状态和格式化测试。
2. 已完成：7,342 条本地标准食品、中文别名搜索、来源和版本信息。
3. 已完成：食材克数、标准食品匹配、菜谱卡片摘要、详情明细和全菜总计。
4. 已完成：设置页六项指标自由勾选，以及设置和营养关联的 ZIP 导入导出。
5. 后续：增加用户自定义标准食材、更多中文同义词和熟重/生重提示。
6. 后续：健身目标与每日摄入汇总；不自动给出医疗化建议。

## 验收重点

- 相同食材、克数和数据库版本始终得到相同结果。
- 单项食材之和与整道菜总计一致，允许误差不超过显示舍入误差。
- 缺克数、缺匹配和缺调味料时有明确提示，不把不完整结果标成精确值。
- AI 关闭或断网时，本地营养计算、查看和 ZIP 备份仍可用。
- 旧菜谱升级后不丢数据；营养字段为空时正常显示“尚未计算”。
- 日志不记录完整饮食内容、身体数据或 API Key。
